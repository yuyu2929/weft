# 现有矢量-栅格空间数据结构调研分析

> 调研范围：工业界主流（OSM/Mapbox/Uber/Google/云原生地理空间联盟）与学术界代表性工作
> （ISPRS 1992 统一结构、武大 QR-tree 2003、GeoInformatica 2024、arXiv 2026 value-quadtree 等）。
> 调研时间：2026-10。每条结论标注了来源类型（论文/官方规范/工程实践）。

---

## 0. 问题定义：为什么"矢量-栅格"值得一种统一结构

企业与工程管线（城市规划、地籍、管线、矿业、遥感监测）长期维护两套数据：

- **矢量**：权威几何、精度可控、拓扑完整、属性结构化；
- **栅格**：分析面（热力、风险、NDVI、噪声）、显式二维关系、集合运算廉价。

二者互相转换有损且昂贵；两套金字塔（瓦片）各自演化，造成：

1. **矢量瓦片切碎要素**（MVT 边界切割）：跨瓦片面/线被裁成多段、属性重复、标注断裂、拾取去重困难；
2. **栅格金字塔不可局部编辑**（COG）：改一个像素要重生成整个文件；
3. **矢栅查询需格式转换**：分析前先栅格化或矢量化，延迟高、精度损失；
4. **索引与存储脱节**：geohash/quadtree 是索引不是存储，R-tree 重平衡写放大。

"统一结构"的目标：**一份表示，同时回答矢量问题（精确几何、拓扑、属性）与栅格问题（覆盖场、区域统计），且支持增量编辑与内容寻址**。

## 1. 网格编码类（Grid coding）

### 1.1 Geohash（base32 位交错字符串）

**思想**：把经纬度区间不断二分，交替取经度/纬度位，交错成二进制串，base32 编码为字符串；**前缀即层级**，同前缀即同格。

| 维度 | 评价 |
|---|---|
| 优点 | ① 极简，无任何依赖；② **KV 存储原生**：前缀范围扫描即空间范围扫描（Redis ZSET、PostgreSQL text index、DynamoDB 都能直接用）；③ 字符串可读、可口头传播；④ 层级递增粒度翻倍，语义直观 |
| 缺点 | ① **矩形面积不等**：赤道格与极区格经向宽度差可达 4 倍，面积统计有偏；② Z-order 局部性在跨层级断裂（相邻格编码不连续）；③ **换日线（antimeridian）断裂**：180° 两侧相邻格编码跳变；④ 邻居计算不对称（东西南北边界行为不同），9-cell 扩展脆弱；⑤ 只编码不存储：要素与格的关系仍需另一套结构 |

**适用**：粗粒度"附近的人"式查询、日志/消息位置索引。不适合面积统计、精密制图。

### 1.2 Quadtree（四叉树，密度自适应细分）

**思想**：把平面递归一分为四，直到每格数据量低于阈值；空区域停止细分（非均匀分布下内存高效）。

| 维度 | 评价 |
|---|---|
| 优点 | ① **密度自适应**：城区密、无人区疏，存储与计算集中在有数据处；② KNN 可用**最佳优先搜索**（优先展开离查询点最近的格，误差有界可早停）；③ 与栅格天然亲和——叶子即瓦片，天然金字塔 |
| 缺点 | ① **非数据库原生**：指针树结构，缓存不友好（每次下落都是一次依赖加载）；② 重平衡非平凡（深度不均时指针 chase 深）；③ 方形近似圆/斜边界差；④ 只做索引，要素存储仍在别处；⑤ 序列化/传输要拉平（linear quadtree 才适合落盘） |

**适用**：内存索引、点云 LOD、游戏引擎。工程落盘通常先转 linear quadtree。

### 1.3 S2（Google，球面单元格 + Hilbert 曲线）

**思想**：球面→立方体六面投影→每面递归四叉→**Hilbert 曲线**编址，30 级 int64；RegionCoverer 用"格并集逼近任意区域"。

| 维度 | 评价 |
|---|---|
| 优点 | ① **局部性最佳**：Hilbert 序下空间邻近=存储邻近，范围扫描缓存/IO 友好；② **正确处理极点与换日线**（球面投影无奇点断裂）；③ 覆盖紧密（RegionCoverer 可用 1~8 级混合格逼近）；④ 工业验证（Google Maps/Firestore/地理围栏） |
| 缺点 | ① **编解码最贵**：球面→面→cell 多步变换，热点路径上有浮点运算；② C++ 为中心，其他语言绑定成熟度参差；③ 四边形对角不对称（neighbor 集合有"对角"例外）；④ **ID 不透明**：int64 无法直接看出层级/位置，调试与 SQL 可读性差；⑤ 只索引不存储 |

**适用**：全球尺度、任意区域的服务端地理围栏/索引。

### 1.4 H3（Uber，二十面体六边形）

**思想**：二十面体投影球面→六边形细分，16 级**全局等面积**；kRing 给出 6 个等距邻居。

| 维度 | 评价 |
|---|---|
| 优点 | ① **等面积**：面积统计无纬度偏置（地理学正确性关键）；② **邻居各向同性**：6 等距邻居，扩散/聚合/KNN 误差小；③ 聚合语义好（surge pricing 式区域聚合） |
| 缺点 | ① **父子包含只是近似**：子格不完全落在父格内（12 个五边形缝合处），多分辨率聚合有损；② 12 个五边形例外让通用算法处处要特判；③ 数据库生态支持少（PostGIS 无原生）；④ 六边形与矩形瓦片/屏幕像素不对齐，渲染要转换 |

**适用**：聚合分析、等面积统计驱动的业务（定价、调度）。

## 2. 磁盘页索引类（Page-oriented indexes）

### 2.1 R-tree / R*-tree（PostGIS 标准）

**思想**：用层级最小外包矩形（MBR）组织磁盘页，叶页存要素 MBR+指针；插入触发分裂（R*-tree 选兄弟最小重叠）。

| 维度 | 评价 |
|---|---|
| 优点 | ① **磁盘页原生**：页大小=IO 块，范围查询读页数少；② PostGIS/Oracle Spatial/SQLite 全线支持，生态即标准；③ 变长要素友好（不像网格被迫均匀） |
| 缺点 | ① **分裂/重平衡代价高**：写放大，随机插入性能随树高退化；② 兄弟重叠导致多路径查找；③ 与栅格/瓦片体系是两套世界（查询栅格要另走金字塔） |

**适用**：通用空间数据库主索引。是企业 GIS 的既成事实，但"重"。

## 3. 瓦片/文件格式类（Tiling & cloud-native formats）

### 3.1 MVT（Mapbox Vector Tile）+ 瓦片金字塔

**思想**：预生成 z/x/y 瓦片，几何量化到 4096 网格、差分+varint 压缩，渲染端零解析。

| 维度 | 评价 |
|---|---|
| 优点 | ① 传输量小、客户端 GPU 友好；② 层级=简化层级，俯视全球到街道无缝；③ 生态统治级（MapLibre/Mapbox/各种 SDK） |
| 缺点 | ① **要素按瓦片边界切割**：跨边界多边形/线被裁成多段，**同一要素在多瓦片重复存储**（buffer 冗余），标注断裂、hover 去重只能靠 id（官方文档明示 duplicated features 与 queryRenderedFeatures 只见已绘制要素的问题；武大学报专文讨论符号完整性问题）；② 层级由全局 zoom 决定，均匀细分浪费；③ 金字塔重生成贵，局部更新=重切一片；④ 属性按瓦片冗余（每 zoom 都带一份） |

**工程实证**（Mapbox 官方文档 / GIS StackExchange / 武大学报 2020）：跨边界 hover 只能先显示局部、~3 秒后靠 filter 才补全；OL3 用户报告标签按瓦片重复。

### 3.2 COG（Cloud Optimized GeoTIFF）+ LERC

**思想**：TIFF 内部分块（256²）+ 概览金字塔前置索引，HTTP Range 按需读瓦片。

| 维度 | 评价 |
|---|---|
| 优点 | ① **单文件云原生**：无需 tile server，S3/R2 直接服务；② 向后兼容全部 GeoTIFF 生态；③ 概览=多尺度栅格金字塔，带宽可控；④ LERC 有损/无损可控压缩 |
| 缺点 | ① **不可局部编辑**：瓦片与概览按规范顺序固化，改一个像素=重生成整个 COG（GISBox/多方工程文档明确指出）；② 仅栅格：无法表达矢量拓扑属性；③ WebGL 后处理兼容差；④ 高延迟小请求堆积 |

**适用**：遥感影像、静态栅格分发。是"栅格侧的 COG 缺矢量子"的经典案例（CloudNativeGeo 2023《Where is COG for Vector?》）。

### 3.3 PMTiles / GeoParquet / FlatGeobuf（矢量的云原生回答）

| 格式 | 思想 | 优点 | 缺点 |
|---|---|---|---|
| PMTiles | 单文件瓦片档案（目录+blob），COG 思想搬到矢量瓦片 | 静态托管、无服务器、CDN 友好 | 继承 MVT 切割问题；瓦片是预渲染视图 |
| GeoParquet | 列式 + 行组统计（bbox min/max 跳过） | 分析扫描极快、压缩率高 | 无内部瓦片/概览；大要素（万顶点边界）整体读取 |
| FlatGeobuf | FlatBuffers 定长记录 + packed Hilbert R-tree | 流式、Range 请求精确取要素 | 同样无金字塔；面向 Simple Features |

CloudNativeGeo 论坛结论：**矢量云原生格式都没有 overviews，矢量 overviews 只能 ad-hoc（丢要素/并要素），无法则化**。

## 4. 学术代表工作

### 4.1 Li Deren & Gong Jianya（ISPRS 1992）：统一矢量-栅格结构

**思想**：一切几何用 **linear quadtree 的 Morton 地址键**表达（点=双 Morton 键、线=路径格集、面=边界+run-length 编码内部）；细分网格提高精度。这是"统一表示"的开创性工作。

- 优点：第一次证明**一份编码可同时读作矢量与栅格**；线性四叉树可落盘可索引。
- 缺点：Morton（Z-order）局部性断裂；只谈编码不谈增量更新/版本；属性与栅格值仍是附属。

### 4.2 QR-tree / QR*-tree（武汉大学 2003-2004）

**思想**：四叉树空间划分 + R*-树页内组织，混合索引。论文实测：插入/删除/查找全面优于 R*-tree，存储略高但数据量越大越接近。

- 优点：把"网格可寻址性"与"页索引变长友好"结合，查询性能显著优于 R*-tree。
- 缺点：仍是纯索引（不含数据存储语义），无版本、无栅格场。

### 4.3 Value-based Quadtree of Rasterized Vector Data（arXiv 2603.23105, 2026）

**思想**：把矢量栅格化为 value-based quadtree，利用自相关性支撑矢量+栅格联合空间分析；实测 Point-in-Polygon 中位延迟降 90%、精度不降。

- 优点：量化证明"栅格化表示可作矢量查询的加速索引且精度可控"——这正是积分栅格思想的实证基础。
- 缺点：仍是分析期转换结构，非存储格式；无跨格要素连续性处理。

### 4.4 Raptor（2025）/ GeoInformatica 2024（Teng 等）vector-raster hybrid

- Raptor：栅格-矢量联合查询**无格式转换**（直接支持 zonal statistics 类操作）。
- GeoInformatica 2024：栅格化保留 pixel-centric 信息做空间查询**候选过滤**。
- 共同点：都承认统一表示的价值，但都停留在"查询引擎层适配"，没有定义**存储层的统一结构与演进协议**。

## 5. 横向对照总表

| 结构 | 可寻址性 | 等面积 | 局部性 | 抗边界断裂 | DB/KV 原生 | 增量编辑 | 要素不切割 | 栅格查询 | 生态 |
|---|---|---|---|---|---|---|---|---|---|
| Geohash | 前缀扫描 | ✗(纬度偏置) | Z序断裂 | ✗(换日线) | ✓ | n/a | n/a | ✗ | 大 |
| Quadtree | 指针 | ✓(同层) | 中 | ✓ | ✗ | 重平衡 | n/a | 叶子可 | 中 |
| S2 | int64 | ✗(四边形不等) | Hilbert✓ | ✓ | 中 | n/a | n/a | ✗ | 中大 |
| H3 | int64 | ✓全局 | 6邻✓ | ✓(无换日线) | 少 | 聚合有损 | n/a | 聚合 | 中 |
| R-tree | 页 | ✗ | 页序 | ✓ | ✓(PostGIS) | 分裂贵 | n/a | ✗ | 最大 |
| MVT | z/x/y | ✗ | 瓦片序 | **✗(切割)** | ✓(瓦片=KV) | 重切 | **✗** | ✗ | 最大 |
| COG | Range 读 | ✓(像元) | 瓦片序 | ✓ | ✓(对象存储) | **✗(整文件重生)** | n/a | ✓ | 大 |
| PMTiles | 目录 | ✗ | 瓦片序 | ✗(继承MVT) | ✓ | 重打包 | ✗ | ✗ | 中大 |
| GeoParquet/FGB | 行组/R树 | ✗ | 中 | ✓ | ✓ | 行组追加 | ✓ | ✗ | 中大 |
| QR-tree(学术) | 混合 | ✓ | 中 | ✓ | ✗ | 索引级 | n/a | 叶子可 | 无 |
| Li-Deren(学术) | Morton键 | ✓ | Z序断裂 | ✓ | 中 | 未定义 | ✓(一次编码) | ✓(run-length) | 无 |
| value-quadtree(2026) | 键 | ✓ | 中 | ✓ | ✗ | 未定义 | 查询期 | ✓(加速90%) | 无 |

**读表结论**：没有任何单一现存结构同时满足——
① 一次编码同读矢量/栅格（Li-Deren 有雏形但无工程化）、
② 要素跨格不切割（GeoParquet/FGB 有，但它们无瓦片无概览）、
③ 增量编辑（COG/MVT 都整片重生）、
④ KV/DB 原生可寻址（geohash/quadkey 有，但它们不等面积或局部性断）、
⑤ 全局局部性（只有 S2/H3 做到，但 ID 不透明且无存储语义）。

**这个交集空位，就是新结构的设计空间。**

## 6. 新结构（Weft）的需求推导

从表格反推，新结构必须同时具备：

1. **网格骨架可寻址**：叶子地址是单一整数（uint64），前缀/范围扫描即空间扫描（继承 geohash 的 KV 友好，但等面积——平面域内同层格子必然等面积）；
2. **Hilbert 序而非 Z 序**：修复 geohash/quadkey 的局部性断裂（继承 S2 的序，但用平面整数运算，无球面变换开销）；
3. **要素一次存储、跨格引用、绝不切割**：格内只存要素 id 与"过格记录"，几何整体存于要素块（修复 MVT 切割；属性不随层级冗余）；
4. **边界缝合账本**：跨格边界的 (cell_a, cell_b, feature_id, edge) 记录，使拾取/合并/reassemble 可精确还原（修复 MVT 去重只能靠 id 且 buffer 冗余的问题）；
5. **叶子积分栅格场**：每叶携带该层在该格上的覆盖场（导出自矢量、可随时重算、带误差界）——栅格查询 O(1)，矢量查询回落到精确几何（继承 value-quadtree 的"栅格加速、精度可控"实证，提升为存储层一等公民）；
6. **叶子级版本 + 脏格增量**：编辑只重写受影响叶（修复 COG 不可局部编辑、MVT 重切一片）；
7. **内容哈希寻址**：每叶内容哈希，确定性序列化——工程管线要可复现、可审计、可 diff。
